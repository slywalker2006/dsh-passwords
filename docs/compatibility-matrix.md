# DSH Compatibility Matrix

## Supported baseline

| Component | Supported version | Validation status |
|---|---|---|
| Node.js | 22.19+ or 24+ | This package's `engines` field. Metadata evidence from the pinned 0.2.1-alpha.2 tree: `@deepseek-ai/libreoffice-kit` declares `node >=22.19.0`; the DSH CLI package itself publishes no `engines`. |
| DSH source/runtime compatibility | `0.2.1` patch line, currently pinned to `0.2.1-alpha.2`; the source gate accepts the single range `>=0.2.1-alpha.1 <0.2.2-0` (the later `0.2.1` prereleases and the stable `0.2.1` release) | The `0.2.1-alpha.2` tree is locked against the official registry and passes the identity gate. Accepting the later `0.2.1` prereleases and stable `0.2.1` is a range/identity guarantee only: no `0.2.1` build has been run through full gateway acceptance. The retired `0.1.x` and `0.2.0` lines, the pre-pin `0.2.1-alpha.0`, and every `0.2.2+`/`0.3` identity are rejected before patching or public startup. |
| Bundled Docker runtime | `0.2.1-alpha.2` | Dockerfile and compose defaults pin the official runtime to `0.2.1-alpha.2`; the release build must verify the bundled package version before pushing the versioned and latest tags. |
| dsh-passwords | 2.7.8 | The 2.7.8 release bundles the Issue #36 installer root-gate fix (fail-closed non-root first install), the Issue #39 inventory scan/timeout fixes, single-scope directory authorization (`allowedFolders`, readable scope doubles as the creation scope when the creation switch is on), DSH `0.2.1-alpha.2` compatibility and gateway/Remote mux hardening. The bundled Docker image and the npm package ship this version. |


Development dependencies declare `>=0.2.1-alpha.1 <0.2.2-0` (the whole `0.2.1` patch line: alpha, beta, and rc prereleases from `alpha.1` up plus the stable `0.2.1` release) and the shrinkwrap locks the resolved tree to the published `0.2.1-alpha.2` packages, so TypeScript resolves the current public plugin APIs without drifting into a later 0.2.x patch or back to the retired `0.2.0` line or the older `0.1.x` head. npm's `alpha` dist-tag and newest published `0.2.1`-line identity is `0.2.1-alpha.2`, so accepting the later prereleases and the stable release is a declared SemVer bound rather than a run -- the alpha.2 subtree is the target actually installed and exercised, and no later `0.2.1` build has passed full gateway acceptance. The package does not impose a runtime DSH dependency: DSH owns the profile and loads this package through its plugin link. Release 2.7.8 keeps the official browse directory picker for both owners and subusers and folds directory authorization into the single `allowedFolders` scope. Runtime startup is fail-closed for the supported `0.2.1` patch line: each identity must pass the settings host-mode and authenticated Cookie-bridge checks; unknown or malformed identities, including the retired `0.1.x` and `0.2.0` lines and every `0.2.2+` release, are rejected before patching or public listeners.

## Plugin surfaces

| Surface | Status | Requirement |
|---|---|---|
| HTTP UI/API plugins | Code-level compatible | The gateway removes only its own authentication cookie and preserves plugin cookies; local regression and test-server lifecycle/provider flows cover the official UI/API path and generic third-party boundary. |
| Plugin combo URLs | Regression-tested | `/plugins/??...` query bytes, including the second `?`, remain unchanged; covered by the version-agnostic regression suite. |
| Plugin business `token` query | Regression-tested | Only the alpha index launch-token context strips bare `token`; plugin paths retain it. |
| Runtime-registered extension endpoint (HTTP or Remote) | Generic direct pass-through | The DSH host reports loaded extension namespaces, Remote streams, and registered routes through one runtime manifest. Subusers do not need endpoint registration or `allow_ssh`; ordinary workspace/session authorization still applies. HTTP and Remote mux extension surfaces are forwarded generically; the manifest adds identification and revocation, not a path allowlist. Subuser WebSocket upgrades follow the separate fail-closed row below. The manifest contains no extension-specific field or path protocol. |
| Registered host/SSH endpoint | Owner-controlled; subuser `allowSsh`-gated on HTTP and WS | `MCP_GATEWAY_SSH_ENDPOINTS` registers legacy host endpoints. `owner:` rules reject subusers on every channel (HTTP, WS, and the Remote mux). For subusers, ordinary registered endpoints require the `allowSsh` switch (off by default, granted explicitly by the owner) on HTTP and WS only. Matching Remote API streams keep the v2.7.5 owner-only per-stream rejection and are not opened by `allowSsh`. Revoking `allowSsh` closes any existing Remote mux carrier immediately. |
| Ordinary extension paths outside the runtime manifest | Generic direct pass-through (HTTP and Remote) | Ordinary `/api` / root-level plugin HTTP requests and Remote mux logical streams are forwarded generically even when they are absent from the manifest. Only the hard-denied host namespaces below and object-level session/workspace authorization restrict them. The pinned 0.2.1-alpha.2 host namespaces productAnalytics, pluginRegistryProbe, and optional speech are blocked for subusers. The gateway does not guess extension names, fields, upload headers, or route semantics. |
| Ordinary extension WebSocket paths | Runtime-manifest gated | For subusers, WS upgrades are allowed for official event channels and loaded ordinary extension routes in the runtime manifest. Unknown routes return `404`, registered host/SSH routes require the subuser `allowSsh` switch (`403` when off), and owners remain unrestricted. |
| Sensitive host capabilities | Independently controlled | Official terminal and registered SSH/host endpoints are owner pass-through and subuser `allowSsh`-gated (off by default); host code execution, plugin management, host telemetry, registry probing, optional speech and native host actions remain outside generic extension pass-through. DSH currently exposes no verified generic SSH capability marker for arbitrary third-party plugins: an unregistered plugin with an unknown namespace cannot be automatically identified as SSH without per-plugin rules. |
| Alpha Remote mux, subuser `workspace/follow` and `session/control` | Code-level compatible | Gateway applies resource filters; local frame tests and test-server lifecycle/multiuser concurrency probes validate the baseline flows. |
| Alpha.1 `workspaceFiles/changes` | Subuser path-scoped | HTTP unary is fail-closed. Remote subscriptions require an authorized session scope and an in-workspace target; `ready/change` frames are validated and out-of-scope absolute paths are dropped without closing the carrier. |
| Alpha Remote mux, subuser `session/follow` and `$events` | Regression-tested | `session/follow` accepts ordinary and subagent addresses; parent access is required, child grants are not; `$events` retains current correlation filtering |
| Official terminal | Owner pass-through; subuser `allowSsh`-gated | Owner terminal HTTP unary methods and Remote mux streams pass through without SSH registration. For subusers, the `allowSsh` switch (off by default, granted explicitly by the owner) gates the surface: when off, `list/environment/shells/close` return local no-capability UX stubs, other terminal RPCs return 403, and mux terminal streams return per-stream `terminal/unavailable`; when on, terminal HTTP unary methods and Remote mux streams are forwarded upstream. Revoking `allowSsh` closes the existing Remote mux carrier and reclaims terminal streams immediately. |
| Official `job` / `account` RPCs | Subuser-compatible with scoped limits | `job/list` and `job/follow` are Remote streams bound to an authorized session; only jobs whose owner matches that session are returned, and `job/kill` is session-scoped. `account/getState`, `getProfile`, `getBalance`, and `account/watch` retain the official read-only host account view under the selected function-first policy. Unknown/future unary account methods and `startSignIn`, `cancelSignIn`, and `signOut` are denied for subusers. |
| `schedule` RPCs | Subuser-compatible with session scope | `list`, `history`, `update`, and `delete` require an authorized session ID. The global `catalog` response is filtered to authorized sessions for subusers; owners receive it unchanged. |
| Workspace ordering | Subuser-compatible with scoped limits | `workspace/insertBefore` waits for the filtered workspace/session baseline when needed; `insertSessionBefore` requires an authorized session in the requested workspace. Success responses are scoped to that same workspace and filter IDs to the caller's visible resources. Ordering is the host DSH registry's global order (not a per-user private order), so an authorized subuser can affect the shared order just as the owner can. |
| Dynamic Cordis runner | Subusers fail-closed | The complete `dynamicCordisRunner` namespace is blocked for subusers, including `runHostHalf`, runner inventory/control methods, known diagnostic methods, namespace roots, and unknown/future methods. This prevents a session-scoped request from reaching host-side dynamic package execution; owner/admin behavior is unchanged. |
| Directory picker | Official browse interaction for all users | The dsh-passwords bundle overrides DSH's platform-adaptive `directory-picker` row with the official `dsh-host-directory-picker-browse` and `dsh-client-ui-directory-picker-browse` pair. This prevents Windows loopback hosts from opening a host OS dialog that remote browsers and subusers cannot use. Both owners and subusers use the web directory list. The owner assigns a subuser's readable directories with this browser, whose browse roots come from `MCP_GATEWAY_DIRECTORY_PICKER_ROOTS` (defaults to the user home when unset; a filesystem root is never a starting point, so the whole disk is never enumerated). Subuser `list/createDirectory` remains constrained by gateway path authorization, and creation follows the same `allowedFolders` scope when the creation switch is on; host `directoryPicker/pick` stays blocked for subusers. |
| Connection Cookie bridge | Test-server verified | `patch status` shows `patched` or `native`; the gateway refuses startup when the bridge is unavailable. |

## Pinned 0.2.1-alpha.2 baseline

DSH `0.2.1-alpha.2` is the bundled Docker target for the 2.7.8 working tree and the current dependency pin for the `0.2.1` patch line, and npm's `alpha` dist-tag and newest published `0.2.1`-line identity -- so the declared `>=0.2.1-alpha.1 <0.2.2-0` dev range resolves and locks to it, while the later `0.2.1` prereleases and the stable release stay unproven in practice until npm publishes them. The runtime gate accepts SemVer prerelease identities from `alpha.1` up, while rejecting the retired lines and the pre-pin `alpha.0`. The `0.2.1-alpha.2` official-registry dependency tree is locked locally.

## Lifecycle contract

For the pinned DSH `0.2.1` patch line target (currently `0.2.1-alpha.2`), gateway startup is fail-closed: the settings host-mode patch and authenticated Cookie bridge must both be present. Missing settings exits with code `35`; a missing or unsupported bridge exits with code `33`; an invalid or unknown DSH release line exits with code `37` before patching. Codes `1`, `30`, `31`, `32`, `33`, `34`, `35`, `36`, and `37` are permanent startup failures and are not retried by the host plugin. The version gate accepts the `0.2.1` prereleases from `alpha.1` up and the stable `0.2.1` release, while rejecting the retired `0.1.x` and `0.2.0` lines, `0.2.1-alpha.0`, and every `0.2.2+` identity; local CLI tests cover the accepted variants and the rejection paths.

Run `dsh-passwords uninstall` before removing the package directory or running `npm uninstall`. It removes only the `dsh-passwords` link and bundle item from the selected web profile, then rolls back only matching hash-protected patches. It leaves `.env`, `data/`, databases, certificates, and unrelated plugins unchanged. If profile dependency reconciliation or patch rollback fails, it restores the original `package.json`, `pnpm-lock.yaml`, and `node_modules` materialized state. The no-DSH case uses stable exit code `34`, independent of `LANG`; the `0.2.1-alpha.2` patch and failure paths are covered by local CLI tests. Browser rendering remains a manual acceptance boundary.
